## Question

Same model (Swift-1.5 INT4), same client, same card (350 W): is HyperQwen's single-user stack (MTP k=4 + int4 heads, DFlash2 + lookup drafting, int8/fp8/KVarN KV) faster or slower than the swift-mk engine, where does each win (decode per prompt class, TTFT, concurrency, context length, greedy parity), and which HyperQwen techniques should swift-mk adopt? Full text in the frontmatter `question`.

## Prediction

Pre-registered 2026-11-01 before any benchmark was run; the numbers are the frontmatter `prediction` (not repeated here so that it cannot drift). Reasoning: HyperQwen's own step is 24.8 ms for 2.8-2.9 tok/step (hq:single-user/README.md MTP table), ours is ~23 ms for 2.9-3.7 tok/cycle plus an exact lookup tail, so we expect us ahead by 1.15-1.5x single-stream; HyperQwen's pooled-slot vLLM design wins concurrency and KV-compressed context.

## Method

**Systems under test (same weights, same card).** Checkpoint `~/models/swift-1.5-int4` (ukisai/Swift-1.5-Qwen3.8-27b, compressed-tensors W4A16 g128 symmetric, bf16 embed / lm_head / MTP, fp8 KV scales). RTX 3090 (sm_86, 24 GiB), driver as on the box, **power limit 350 W for everything** (HyperQwen's published numbers are at 250 W; `nvidia-smi -pl` needs sudo, so it was left alone: SM clock / power are logged per run and discussed in Results). One GPU lease for each batch of visits, `nvidia-smi` empty between visits.
- **swift-mk** = `server/serve.py --prompt-lookup auto` (repo HEAD, engine K11, int4 head + exact bf16 rescoring, MTP chain k=3 + prompt-lookup tail T<=8, bf16 KV, max-model-len 28672; `ours-fp8` = `--kv-cache-dtype fp8 --prompt-lookup 0 --max-model-len 65536` for the long-context rows). Served name `swift`, port 8000.
- **HyperQwen** = the unmodified image `ghcr.io/syv-ai/hyperqwen:latest` (vLLM 0.30.0 + 45 patches), `entrypoint single` with `PREPARE=0 VERIFY=0` (the prepare stage would download the base model), our own `docker run` flags only (`hq.sh`: no env_file, no token, `HF_HUB_OFFLINE=1`, port published on 127.0.0.1 only, models bind-mounted read-only). Served name `qwen3.8-27b`, port 18020. Configs: `mtp-fast` (`SPEC=mtp CTX=fast`: k=4, bf16 KV, split-KV verify, 64k), `dflash2` (`SPEC=dflash2`, DFlash2 W4A16 drafter, 7 drafts, lookup on, 8 slots / 64k), `dflash15` (`DFLASH_TOKENS=15`, 4 slots / 56k), `mtp-long` (`CTX=long`: fp8 KV on FlashInfer, k=3, `MAX_LEN` 150000 or what fits), optional `dflash2-long` (int8 KV).
- **Adaptation of HyperQwen to our checkpoint (what had to change, none of it touches the image or the sources)**: HQ's requantisation pipeline assumes its own base checkpoint and writes in place (`.bak-orig`, ~20 GB; `prepare/quant_heads_stream.py`) and `docker/prepare.sh` would download `dbirks/Qwen3.8-27B-W4A16-AutoRound`. Disk is 5 GB on <data-disk>. I checked on CPU that Swift-1.5's embed_tokens / lm_head / MTP module are *the base model's* up to quantisation noise (random 4,000 rows: embed int8-requant relative error 0.0067, lm_head int4 0.145, `mtp.fc` int4 0.154, `mtp.q_proj` int4 0.151: pure quantisation error, `cmp_heads2.py` in this folder), so I assembled a HyperQwen "fast variant" layout by `build_model_dir.py`: Swift body shards 2-4 symlinked, shards 1 and 5 rewritten without the bf16 embed / lm_head, HQ's int8 embed, int4-GPTQ lm_head, int4-GPTQ MTP module, 40,960-row draft head and its id list reused unchanged from `~/HyperQwen/models/Qwen3.8-27B-W4A16-AutoRound-fast` (read-only; calibrated on BASE hidden states and base outputs, **not** on Swift's: not re-done, because the GPTQ capture needs ~74 GB scratch and hours), `config.json` = Swift's + HQ's `group_1..3`, Swift's fp8 `kv_cache_scheme` kept. DFlash2 drafter = HQ's W4A16 `Qwen3.8-27B-DFlash2-W4A16` (trained on base). The result is 2.8 GB of new files in `runs/hq/swift-fast` (ignored). Chat template: Swift's (HQ's `translate_chat_template` / `harden_chat_template` steps were skipped); the client sends token ids, so the template is applied identically client-side for both servers.
- **Same client, same prompts** (`run.py`): httpx streaming `/v1/completions` with token ids, `ignore_eos`, `return_token_ids`; decode tok/s = (tokens after the first chunk) / (t_last - t_first) (E0 definition, `server/bench_server.py`); TTFT = request sent -> first token chunk. Prompts frozen as ids (`results/prompts_manifest.json`): **E0** code / prose / math (33 +-1 tokens, 385 new) and the 8K summarisation (8,030 tokens from `topics/*.md`), **E6**'s 32 tasks (a code edits 8, b log extraction 6, c agent tool-call turns 6, d prose 6, e math 6; prompts 0.2-7k tokens), **E8**'s 48 English tasks (qa ex sm tr em mt cd ag; 33-1,100 tokens), 256 new tokens for E6 / E8. Greedy (`temperature 0`) and T=1 (`top_p .95, top_k 20`). TTFT: 20-token plain prompts (8 distinct slices) and the 8K prompt with a unique 1-token prefix per rep so no prefix cache / snapshot can hit.
- **Interleaving / reps**: rounds of `[ours, mtp-fast, dflash2, dflash15]` each started from scratch (server boot, warm-up of 6 requests that are discarded, then the suite), three rounds, so each server is measured 3x with the clock / thermal state shared. Concurrency (C = 1, 2, 4, 8; 192 new tokens; short E8 prompts and distinct ~3.9k-token prompts, 2 rounds per cell), long context (needle `copper-lantern-4912` at 40 % depth of a 27.9k / 55.9k / 99.9k-token prompt built from repo markdown, 160 new tokens, EOS honoured) and parity (first 128 greedy tokens of the first 30 E8 tasks and of the 32 E6 tasks, round 1 of each server vs ours) are separate visits / derived from the greedy runs.
- **Safety / hygiene**: the former `hyperqwen-single-1` container (its environment holds an HF token) was never inspected, started or logged; nothing under `<data-disk>/llm` or docker volumes was deleted; the `hyperqwen_qwen-cache` volume (3.9 GB before) was re-used for compile caches.

**Ranked techniques worth adopting in swift-mk** (gain = estimate, [I] unless a measured number is cited; effort = engineer-days of a CUDA-literate agent):

1. **A DFlash2-style one-pass block drafter in the engine** (highest value). Measured: HyperQwen's DFlash2 on *our* Swift-1.5 weights reaches 5.83 / 5.20 tokens per step on E0 code / math at 23 ms vs our chain's 3.50 at 21 ms: x1.5 / x1.36 single-stream decode on non-copy code and math, x1.14-1.24 on E6 / E8; prose unchanged. The engine already verifies T = 8 rows per step (K11, V(8) = 21.6 ms); the drafter adds ~1.2 GB of W4A16 reads (~1.3-2 ms) but removes our 3-step chain draft (~2.3 ms), so ~22 ms / step is plausible: code ~5.8 / 22 ms = ~265 tok/s [I]. Needs: the 5-layer drafter forward (hidden states of layers 5 / 19 / 33 / 47 / 61, fc, dynamic convs, 2,048-token window, 16-candidate selector; reference = vLLM's native DFlash2 `hq:docs/optimizations.md:204-232`, Apache-2.0 code, drafter weights from incoai, licence not stated: check before shipping), W4 g128 GEMV kernels (we have them), a Swift-1.5-specific acceptance check (it works unmodified here; distillation on Swift's own outputs may lift it), exact verification (greedy leading match, K7 sampling with a point/sparse-support q). Combine with our exact PLD tail for copy-heavy cells. Effort 8-15 days; risk = selector semantics and the hidden-state taps inside our fused graph.
2. **Free ~2.5 GiB of VRAM -> context** (cheap). HyperQwen's server holds 85k tokens of bf16 KV next to 13.97 GiB of weights (M, container log); we stop at 28,672 because we keep a bf16 embed (2.54 GB), a bf16 head for rescoring (2.54 GB), an int4 head copy (0.59 GB) and a 9-slot ring (0.62 GB). Options: int8 g128 embed (HyperQwen: PPL unchanged to 3 decimals, C; relative row error 0.0067, M here) = +1.27 GB; or keep the bf16 embed / rescoring head in pinned host memory read through mapped UVA (a handful of 10 KB rows per step: ~tens of us [I], exact) = up to +5 GB ≈ +70k tokens of bf16 KV at ~70 KB per token. Effort 2-4 days, no change to the model's greedy output with the UVA variant.
3. **Quantised KV for 100k+ context** (C: KVarN k4v2 g128 13 KB/token, PPL +0.16%, decode tax 2.13x at 112k depth; int8-per-token-head 33 KB buys no space over our fp8; stock vLLM `int4_per_token_head`: pool 355k vs 164k tokens for fp8 at 0.93 util on HyperQwen's box, `hq:docs/long-context.md:444-446`). Only if long-context sessions are a goal; fp8 already doubles our context. Effort 10+ days (new attention-KV layouts in K2 + prefill gather); not measured here.
4. **A second look at the draft side of the lookup**: HyperQwen's lookup is keyed on the last 6-12 *committed* tokens over the whole history and fills up to 15 positions, ours on the chain's drafts with <= 4 tail tokens; their 381 tok/s claim is a verbatim-copy cell and was not reproducible here (dflash15 failed), so the value of widening our tail beyond T = 8 on verbatim copy is unmeasured. Effort 3-5 days for a T = 16 graph width; do after measuring.
5. Not worth it for single-stream: batching / continuous scheduling (our identity is the bs = 1 graph; effort months), W4A8 / `INT8_ACT` prefill (C +13-30% prefill at PPL +4.1%: we already prefill 8K at 2,050 tok/s without it), int8-QK prefill attention (C: 0-3% standalone, negative on one 3090), their 40k draft vocabulary (ours is 64k + 3.3k extension rows and costs nothing measurable), unrescored int4 head (M: greedy parity 7 / 30).

**Caveats that bound these conclusions.** Two rounds, n = 1 prompt per E0 class; the GPTQ heads, draft vocabulary and DFlash2 drafter are *base-model* artefacts reused on the fine-tune (HyperQwen's third-party doc says re-calibrating on the fine-tune is "the stronger option", `hq:docs/third-party-checkpoints.md:51-57`), so HyperQwen's numbers here may be a lower bound; our bf16 embed -> HyperQwen's int8 embed, int4 heads and fp16 state mean it serves a slightly different target than ours; the 350 W vs 250 W question is open; no long-context, concurrency or copy-ceiling data.

## Conclusion

**Answer.** On our own Swift-1.5 INT4 weights, through one HTTP client and 350 W, HyperQwen is *not* the slow baseline the pre-registered prediction assumed. Its MTP mode ties swift-mk on E0 (code 174 vs 166, prose 104 vs 107, math 177 vs 166, 8K 139 vs 131 tok/s) and its **DFlash2 mode is x1.53 / x1.36 faster on E0 code / math (254 / 225 tok/s), x1.14 on E6 agent / log / edit tasks and x1.24 on the 48 E8 English tasks**, at the same ~22 ms step, because a one-pass 7-token block drafter delivers 5.2-5.8 tokens per step where our MTP chain delivers 3.5; on prose all three stacks tie (103-107 tok/s). swift-mk wins TTFT (39 vs 53-56 ms short, 3.9 vs 4.2 s at 8K), deterministic exact greedy against a bf16-rescored head (HyperQwen's greedy output differs from ours within 128 tokens on 23 / 30 E8 prompts) and class-c agent turns (240 vs 229). Context (HyperQwen pool 85k bf16 tokens vs our 28,672) and concurrency are HyperQwen's by design; their long-context decode rates and the 381 tok/s copy ceiling were **not measured** (stopped by the human; `dflash15` failed to serve). The pre-registered prediction "swift-mk wins >= 3 of 4 E0 prompts by 1.15-1.5x" is **refuted** (1 of 4). The most valuable thing to take from HyperQwen is the DFlash2 block-drafter architecture (est. x1.3-1.5 on code / math [I]), then a VRAM diet that buys context for free, then quantised KV.

**Confidence: medium** for the single-stream decode / TTFT ordering (two interleaved rounds, spread <= 1%, same client, same power class), **low** for everything about context, concurrency, copy-ceiling and parity cause (unmeasured or one-sided).

## Dead ends

- **`DFLASH_TOKENS=15` (`dflash15`, the 381 tok/s claim) did not serve**: both rounds booted (176 s cold / 34 s warm), `/health` came up, the first warm-up request returned HTTP 200 but the SSE stream carried no `token_ids` chunk (client: `RuntimeError('no tokens')`). Not diagnosed (the container log shows only `POST /v1/completions 200 OK` lines and an `expandable_segments ... OOM while trying to map 20 MiB (free 34 MB)` allocator warning also present in the working `dflash2` boot, `runs/hq/logs/container-215816.log`); candidates: this checkpoint's weights are 1 GB lighter than the constants behind the 4-slot / 56k profile (`KV_MEM` is pinned in bytes), the lookup-filled 16-token block with `return_token_ids`, or the adaptive block under `--no-async-scheduling`. The `DFLASH_TOKENS=15` row of the gap table is therefore *unknown*, not "worse".
- **Stopped early (human, "wrap up now") before round 3, the concurrency sweep, long-context (28k / 56k / 100k), `CTX=long` / `huge`, TTFT sweep, ours-fp8**: the harness (`run.py visit <server> --suite conc|long|ttft`) and `hq.sh` configs (`mtp-long`, `mtp-huge`, `dflash2-huge`) exist but never ran.
- **Prediction miss, not a bug**: I expected HyperQwen at 250 W-class claims (121-131 tok/s C1 from its docs) and priced it at 125 / 130 tok/s on E0 code; at 350 W on code-like prompts it ran 174 / 254. Their 127 tok/s headline is a chat-cohort figure (8 prompts of 45-300 tokens, 1,024-token answers), not a code prompt; the E0 code prompt is a memoised-Fibonacci snippet that the model writes with high predictability.
- **K11's "240 tok/s" pooled a-c did not reproduce** through this client (197 pooled median at 256 new tokens; class c 240 does match). Different aggregation (K11: mean over longer outputs, engine-direct) and the HTTP client; not chased.
- **Heads / vocabulary / drafter were not recalibrated on Swift-1.5** (GPTQ capture ~74 GB scratch, hours): base-model artefacts reused after checking on CPU that Swift's embed / lm_head / MTP are the base model's (relative error equals pure quantisation error). HyperQwen's own docs say the recalibration is "the stronger option".
- Process: `pkill run.py` left the swift-mk server of the aborted round-3 visit running (orphan, killed by hand, GPU back to 420 MiB); `hq.sh stop` first overwrote a single `last-container.log` so the first `dflash15` container log is lost (fixed for later visits); the `grep -v` in the driver block-buffered the log so the first visits were invisible for 40 minutes.
- Disk: `<data-disk>` fell from 7.7 GB to 4.0 GB free (2.7 GB `runs/hq/swift-fast`, +0.8 GB compile cache in `hyperqwen_qwen-cache`); nothing was deleted. `runs/hq/swift-fast` (2.7 GB, ignored by git) can be removed by the human when the follow-up below is done.
