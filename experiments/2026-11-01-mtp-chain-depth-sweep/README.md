# mtp-chain-depth-sweep

## Question

See frontmatter (written before any run).

## Prediction

Frozen in the frontmatter (committed before the first deep-chain measurement). Headline bets: cycle +1.05 ms per chain depth; code / math k = 5 fixed +8%, prose -2.5%; k = 5 + tail <= 2 loses 7% to k = 3 + tail 4 on copy-heavy classes a-c; a width-only gate cannot recover prose to >= 0 (sunk draft cost), an adaptive draft depth can (p = 0.6).

## Method

**Engine.** swift-mk HEAD (last engine commit `a2f79e4`, tmax = 8 engine = 9-slot DeltaNet ring, K9 int4 head + exact rescoring, bf16 KV, default draft list `draft_vocab_ext_68864.npy`), model `~/models/swift-1.5-int4`, one RTX 3090, lease held for every timed run. The committed engine sources are untouched.

**What was run, what was not (parent wrap-up order, lease contention).** RUN: library patch + build, `test_deep.py` (parity, first library revision), one 84-minute GPU session = `base,k3,k4,k5,k6,k7` (greedy, no tail) on all 132 tasks + the cost grid at three contexts, the offline gate model (CPU) on its cycle logs. IMPLEMENTED BUT NOT RUN: the tail configs (`k<K>t1`, `k<K>t2`), the online gate (`g<K>...`, adaptive depth modes 2 / 3), T = 1 sampling (all of it, incl. `test_sampling_gate.py`). The Method text below describes the whole design; sections of it that were not exercised say so in Results.

**Does the engine support chain depth > 3?** Partly. The device layout already carries 8 rows (`ds` tokens / outputs, `hr` / `cat` buffers of 8 rows, `SS_MTOK` 8 tokens, `SMK_SPEC_PMAX` = 7 = chain + tail) and `smk_spec_run` accepts k up to 7, but `nchain(k) = min(k, 3)` (src/mtp.cu:342) makes everything above 3 a *prompt-lookup tail* (`smk_spec_run_pld` hard-codes `SMK_SPEC_KMAX` drafts into the mailbox / proposer), `spec_finish` only fills the MTP positions of chain passes 1-2 (`ss[SS_DPOS+1..2]`, src/mtp_sample.h:82), and `smk_spec_start` refuses k > 3. So chain depth > 3 needs a change. It is **opt-in and private**: `lib/deep.patch` (applied to `git archive a2f79e4` by `lib/build.sh` into `runs/lib/`, 392 diff lines) adds, without changing any existing entry point's behaviour:
- `spec_finish` / `k_start` fill `ss[SS_DPOS + 1..8] = P + a + j - 1` (positions of chain pass j; ss[4..11] were unused);
- new cycle graphs `deep_part(kc, kv, which)` = verify T = kv + 1 rows (kv = 0..7; chain drafts + tail tokens) + accept + MTP catch-up of kv + 1 rows + **kc chain drafts (1..7)** + the confidence kernel `k_conf` (softmax max-prob of the restricted head logits `lg`, and the max prob of the processed proposal q in sampling; 1 block, ~4 us per draft) + a mapped-memory report of tokens / drafts / confidences; sampling: the tail tokens beyond the `nch` chain drafts are delta proposals chosen by a device scalar (`k_delta_q_dev`), so the graph does not depend on the gate's decision;
- `smk_spec_run_deep` (host loop, one round trip per cycle like K11's `smk_spec_run_pld`): gate (verify the leading drafts whose confidence passes tau_1..tau_j), tail (existing proposer, anchored at the last verified chain draft, <= 7 - nch tokens; or `tail priority`: first try chain 3 + tail 4, deep chain only if the proposer has no match), adaptive draft depth, per-cycle log (a, nch, tail length, confidences); `smk_spec_deep_begin / _prewarm / _launch / _log / _stats`.
Driver: `deep.py` (ctypes on top of the committed `spec.py`, `SMK_BUILD=runs/lib/build`), benchmark `bench_deep.py`, tests `test_deep.py` (greedy == plain T=1 greedy on E0 code / math / prose and E6 a2 / b1 / c3, 192 tokens, for fixed K = 3 / 5 / 7, tail modes 1 / 2, gate with fixed and random tau, adaptive depth, forced partial acceptance up to 8 rows: every divergence is the documented prose rounding near-tie; `results/test_deep.log`).

**Workloads.** E0-style prompts (code / prose / math / long8k, 384 new tokens, `bench_spec.prompts`), E6's 32 tasks (classes a code edit 8, b log / tool output 6, c agent turns 6, d prose 6, e reasoning / math 6; prompt ids from `experiments/2026-10-31-ngram-draft-potential/runs/trace`, stop at the canonical greedy length or EOS), E8's 48 English chat tasks (task set not included in this release; the original suite also ran a matched second-language arm that is omitted from every table here; stop at the canonical length / EOS). Greedy and T = 1 sampling (top_k 20, top_p 0.95, sampled chain drafts, `draft_sample = 1`).

**Configs** (`bench_deep.py` grammar): `base` = committed async k = 3 cycles (`smk_spec_run`); `k<K>` = deep driver with chain depth K and full-width verify; `k<K>t1` = + prompt-lookup tail after the chain (`<= 7 - K` tokens: K = 3 / 4 / 5 / 6 / 7 -> tail <= 4 / 3 / 2 / 1 / 0); `k<K>t2` = tail priority; `g<K>[a<L>][t1|t2]` = confidence gate (+ adaptive depth). Configs are interleaved per task, reps alternate the order, graphs of every (K, width) are captured before any timed run. Rate = tokens emitted up to the target / decode wall time (prefill and the first draft stage excluded), pooled over the class, median over 3 reps (E0, E6) or 1 rep (E8: deterministic greedy streams, 36K tokens per config); 95% CI = bootstrap over tasks (2000 resamples, per-task time = median over reps); E0 classes are single prompts (range over reps reported).

**Gate.** Confidence of depth j = max softmax probability of the draft head's logits at that depth (`raw`; sampling: max probability of the processed proposal q, known before the draw, so the stop decision depends only on earlier drafts and the distribution at j, never on the sampled token: the emitted distribution stays exactly p). Rule: d_j is verified iff conf_i >= tau_i for all i <= j. tau (7 values) fitted by coordinate descent on the offline model (`gate_model.py`: renewal-reward over the logged cycles of the full-width K = 7 run, measured cost grid C(K_draft, width), objective = mean over the 11 classes (one omitted from the published tables) of log(rate / rate of fixed k = 3)), 4-fold cross-fit by task (class-balanced round robin; a task is gated with the tau of the model that did not see it), `mean` and `safe` objectives (`safe` = a loss in any class costs 5x). The gate only saves verify rows: the drafts are computed by the cycle graph before the host sees the confidences, so the draft cost of unused depths is sunk; adaptive depth (`a<L>`) lets the host pick the next cycle's chain depth (K if this cycle's gate kept >= L drafts, else L) from the confidence profile.

**Cost model (modelled vs measured).** Cycle ms vs (chain depth, verify width) = replays of the deep cycle graph (`results/cost_grid.json`, ctx ~ 40 / prompt length of a1 / 8000) - measured; K11's V(T) table (`BENCH.md` K11: V(4) 19.6, V(8) 21.6 ms at ctx 64) is the cross-check. The gate model uses the grid; every table says whether a number is modelled or measured.

## Conclusion

**The k = 3 default is too shallow for everything that copies or computes, and too deep nowhere below k = 4.** On the real engine (greedy, same graphs, same host loop, 132 tasks) k = 4 is a pure win: no class below x0.996 (E0 prose x1.012, E6 d x0.996 [0.970, 1.029]) and +5..+20% elsewhere (E0 code +12%, E6 a / b / c +14 / +17 / +20%, e +11%, English +6%) for +0.9 ms per cycle. Deeper keeps paying on code / math / copy (k = 7: E6 a / b / c x1.35 / 1.41 / 1.57, e k = 6 x1.20) and loses on prose-like work (k = 5: E0 prose x0.957, E6 d x0.991, E8 prose-type tasks x1.012; k = 7: x0.85 / x0.90), with long8k at k = 5 (+6.9%). The per-class optimum differs by 3 depths, so the best static default is k = 4 (never loses) and the best system is an adaptive controller; modelled with a cross-fitted EMA depth controller + a confidence width gate it keeps prose / d within 0.2-1.1% of k = 3 while taking x1.20-1.59 on e / a-c - a model, not yet measured.
