# ngram-draft-potential

## Question

Can prompt-lookup (PLD) / n-gram drafting (copy what followed an earlier occurrence of the last n tokens) add speculative acceptance on top of the engine's int4 MTP head (k=3, T=4 verify, `engine`) on realistic coding-agent / editing workloads whose output reuses the context, without losing on workloads that do not (free-form prose, reasoning/math)? And what end-to-end speed-up does a hybrid draft policy give when the verify step may carry up to T=8 rows? Decision rule (pre-registered, frontmatter): recommend implementing iff the pre-registered hybrid H0 gives pooled a-c >= 1.10 (CI lower bound > 1.05), each of a/b/c >= 1.05, and d/e >= 0.99.

## Prediction

Frozen in the frontmatter (commit `510a951`, before any engine run; the 32 prompts, `workload.py` and the analysis code were committed afterwards, before the first trace was analysed; the class-c prompts were revised twice afterwards, see Dead ends). Summary of the bets: MTP-only E 3.5 / 3.1 / 3.3 / 2.2 / 3.2 tokens/cycle (a/b/c/d/e); primary hybrid H0 / MTP-only tok/s 1.20 / 1.10 / 1.05 / ~1.00 / ~1.00 (pooled a-c 1.13); PLD-only 0.85 / 0.70 / 0.60 / 0.45 / 0.45 and never above H0; PLD limited to L=3 (T=4) <= +4%; oracle best-of 1.35 / 1.25 / 1.18 / 1.08 / 1.07; recommend = YES (60%), class c the likeliest miss. Scorecard against the outcome in Results.

## Method

**Engine / what is measured.** `engine` at `ba31ad5` built privately (`git archive` + `make`, `~/llm-lab/e6_engine`, other agents edit and rebuild the live tree), K5 GEMV + K6 fast prefill (`FastPrefill`) + K4/K7 MTP cycles (int4clip MTP layer, 64k int4 draft head), bf16 KV, greedy, thinking off, RTX 3090 under the lab GPU lease (01:01-01:12 and 01:24-01:26, 01:45-01:47 on 2026-11-01; server not running, lease released each time; ~0.35 GPU-hours incl. model loads). `run.py gen` runs every prompt twice:
- **N (natural)**: k=3 MTP cycles, one cycle per host sync; per cycle the number of accepted drafts (draft position i accepted iff accepted >= i).
- **F (forced single-row cycles)**: `set_force([1])`: every cycle verifies [anchor, d1, d2, d3] but accepts only the anchor's successor, so EVERY position of the greedy continuation is a cycle start. Per position the run records the anchor, the MTP drafts d1..d3 (device state read before the cycle) and the engine's natural accepted count m_i (histogram delta). So MTP acceptance is measured at every position, not just at the positions a particular policy visits. F's token stream is the canonical continuation.
- Validation: the prefix match of the recorded drafts against F's continuation equals the engine's own natural count at **99.71%** of 20,000 positions (the sum over all tasks) (`mtp_m_agreement`); simulated MTP-only E (walk with per-position acceptance) vs the natural run's E per class: 3.696/3.696 (a), 3.693/3.699 (b), 3.923/3.934 (c), 2.326/2.346 (d), 3.486/3.475 (e). N and F token streams are identical in 24/32 tasks; 8 diverge after 98-711 tokens (a5, d3-d6, e3-e5: rounding near-ties between the T=4-row verify at different row offsets, as in MTP_PARITY.md) and F is used.

**Workload** (`workload.py`, 32 prompts through the chat template, <= 768 new tokens, EOS stops; `results/workload.json` has sha256 + sizes; everything from `projects/swift-mk` is read at `ba31ad5`): (a) 8 code edits on 3.4-5.6K-token files of `vendor/` / `experiments/` (rename function: full file, add type hints: full file, add logging: full file, injected bug -> unified diff, injected bug -> corrected function, rename class+methods -> unified diff, validation+docstrings -> two methods, refactor into a dataclass + call-site diff); (b) 6 log / tool-output tasks of ~2.4-4.3K tokens (git log --stat -> table, nvcc ptxas log -> table, numerical check log -> filtered lines, traceback log -> error summary, test output -> table, parity log -> table); (c) 6 agent turns with the Qwen tool template (system prompt + tool schema + earlier tool call + tool result of 1.2-3.7K tokens: one `edit_file` per grep hit, `write_file` shell script from an `ls -R`, `edit_file` calls with quoted anchors from a `read_file`, one `bash` commit command quoting a real `git show` diff, `write_file` TODO report, parallel `read_file` calls); (d) 6 prose/QA (2 with a ~2-3K-token background document, 4 short prompts); (e) 6 reasoning/math (short prompts). The 'full file' tasks emit only the first 768 tokens of a 3-6K-token output (copy position 0..768 of the file, not the whole file). Natural outputs shorter than the 384-768 target: a4 336, a6 360, b4 204, b5 437, c1 109, c4 37, c5 53 (see Dead ends for class c).

**Offline simulation** (`analyze.py`, CPU, `results/trace.npz` holds prompts, continuations, drafts, acceptance). At every cycle start i (anchor g_i) a drafter proposes tokens for g_{i+1}..; greedy verification accepts the longest correct prefix r and emits r+1 tokens (exact against the real continuation, no sampling). PLD: query = last n tokens of prompt+generated-so-far (n=4,3,2 longest first, or n=1 with a longest-suffix-match preference), candidates = earlier occurrences (known tokens only, the proposal never reads the real future), 'recent' or 'longest' (backward-extended agreement l, <= 64, <= 64 most recent candidates), up to L=3,5,7 following tokens. Policies: MTP-only (k=1,2,3), PLD-only, switch hybrid (use PLD iff l >= m else MTP chain k=3; **H0** = n 4..2 recent, m=3, L=7, fixed in the prediction), MTP chain + PLD tail (rows = anchor, d1..d3, then <= 4 PLD tokens found by matching the n-gram that ends at d3; accepted only if all of d1..d3 were right), oracle best-of (per-position choice of the cheaper-per-token of MTP / PLD; upper bound), grid over (n config, m in 1..12, L) with variants, 2-fold cross-validation over tasks (tune on one half by the mean of the five class ratios, evaluate on the other; optionally with the rule's no-loss constraint on the train fold).

**Cost model (MODELLED, not measured for T>4).** Verify step V(T) = 20.195 / 20.721 / 21.077 / 21.545 ms for T=1..4 (K5, `engine/BENCH.md`) and for T=5..8 V(4) + the E3 whole-step GEMV growth (`experiments/2026-10-30-w4-multirow-verify-and-power/README.md`: 18.93 -> 19.09 / 19.62 / 19.985 (interpolated) / 20.35 ms) + 0.2 ms/row DeltaNet snapshots (K1: 0.51 ms at T=1, 1.15 at T=4) + 0.02 ms/row attention = 21.93 / 22.68 / 23.26 / **23.85** ms for T=5..8. MTP cycle overhead 0.275 ms (accept + catch-up) + 0.427 ms per draft step (K4: 0.43 ms, k=3 -> 1.28 ms) + 0.03 ms per catch-up row beyond 4; MTP-only k=3 cycle = 21.545 + 0.275 + 1.28 = 23.10 ms (= the K7 greedy cycle 23.10 ms, 151.5 tok/s at E=3.50). Host-chosen graph per cycle = +0.2 ms/cycle on every hybrid cycle (MTP cycles included); MTP drafts are always computed (variant B: on-device decision, no host sync, drafts skipped when the next cycle will use PLD). modelled tok/s = tokens / sum of cycle ms (first token and prefill excluded), per class pooled over its tasks; ratios = policy over MTP-only on the same positions; 95% CI = percentile bootstrap over TASKS (10,000 resamples, 6-8 tasks per class: wide).
Model check against the engine (measured, N run, one cycle per sync, runs that hit the 768-token cap): 22.97-23.10 ms/cycle for short prompts (model 23.10; the 1-cycle-per-sync penalty is not visible), 23.31-23.58 ms/cycle with 3.4-5.6K-token contexts (+0.2-0.5 ms context-dependent attention that the model, calibrated at ctx ~64, does not include; it applies to every policy).

**Baseline / ablations.** Baseline MTP-only k=3 (also k=1,2 and plain T=1 in the table). Ablations: PLD only, L in {3,5,7}, host-sync 0/0.2/0.5 ms, V(8) in {24 (model 23.85), 26, 28, 30}, draft-skip variant B. Budget: ~0.35 GPU-hours, ~25 min analysis.

## Conclusion

**Answer.** PLD alone is not a drafter for this engine (x0.80 on a-c, x0.43-0.50 on d/e). PLD *replacing* MTP by a match-length gate (the pre-registered H0) gains +17% / +3% / +21% on code edits / log extraction / agent turns but loses 3% on prose and **12% on math**, so the pre-registered rule says do not implement it. The reason is the MTP head itself: on these workloads it already accepts 3.7-3.9 tokens/cycle (87-97% of cycles accept all three drafts on copy-heavy classes), so the only thing PLD can add is depth beyond T=4, never better first tokens. The policy that captures it is **MTP chain + PLD tail (T up to 8)**: modelled **x1.15 (honest held-out, no-loss constrained, [1.06, 1.25]) to x1.37 (in-sample best cell, [1.27, 1.48]) pooled on a-c** at V(8)=23.85 ms, d 0.995-0.991 (-0.5 to -0.9%), e +2 to +5%; tok/s MTP-only 160/160/170/101/151 -> 219/211/247/100/158 (E3 cell). It satisfies the decision rule's thresholds (the rule was written for H0, this variant is exploratory and its cell choice is partly post-hoc; the held-out CV with the no-loss constraint is the number to believe). Pooled a-c stays above x1.10 up to V(8) ~ 33 ms, but the no-loss clause on d/e only holds up to V(8) ~ 27 ms; the unverified input is V(T=5..8) and the T>4 kernels. **Recommendation: implement the MTP chain + PLD tail (not H0)** as an opt-in, workload-adaptive path, after measuring V(T) for T=5..8 on the real graph (a 2-hour kernel/graph task); if measured V(8) <= 26 ms the model gives >= +25% on copy-heavy agent/edit traffic, if V(8) >= 30 ms it is <= +18% pooled on a-c and d/e start to lose (gate m must rise).

**Not shown / caveats.** (i) Everything about T>4 steps is modelled (V(T), catch-up, sync); numerics of T=8 rows may flip near-ties (as K5/K7 found for T=1 vs 4), which changes the trajectory not the acceptance statistics. (ii) 32 tasks from one repo and one model; 6-8 tasks per class, wide CIs; the 'full file' tasks are 768-token prefixes; classes d/e with short prompts have no context to copy by construction (a long-context e/d would raise PLD's rate a little, but those are the negative controls). (iii) Selection: the CV-tuned and in-sample numbers are over a ~600-cell grid (`grid`), reported with the held-out CV; the d-class cost (-0.5..-2%) is real but small and could be removed by an adaptive back-off (skip the tail for N cycles after a wasted tail; not simulated). (iv) Greedy only; with sampling (K7) PLD tail tokens are deterministic proposals (q = delta), the existing delta-draft acceptance path (`draft_sample = 0`) applies, but acceptance under T=1 sampling is lower; not measured. (v) Thinking-off, one prompt per task, chat template as served.

## Dead ends

- **Agent-turn prompts took three iterations.** v1 (plain task text) produced 29-79 token *exploratory* first calls (`grep`, `git status`, `sed -n`) on 5 of 6 tasks, far below the 384-768-token window (kept in `runs/trace_v1/`, not committed): the model investigates before acting even when the tool result is complete. v2 added 'do not explore, your next message must be the tool call(s)' and 'one edit_file per hit': c2/c3/c6 became 559-768 tokens, c1/c4/c5 still 37-109. v3 added a system prompt asking for a short plan and forbidding re-confirmation: no change in c1, c4, c5 (109 / 37 / 53 tokens; the final set). The shipped class c therefore has three long copy-heavy turns (c2, c3, c6: 570-768 tokens) and three short ones. Prompt changes targeted output length only, but I had seen the preview analysis of the v1 (and 26 other) traces before v3 (its class-c numbers were similar: H0 1.19, E3-like 1.3-1.4), so class c is not blind. The class-c ratios are the least reliable: three tasks with <= 109 tokens contribute little weight to the pooled ratio (9% of class-c tokens).
- **Natural-run harness artefact.** `N` kept launching cycles after an EOS inside a cycle until 768 tokens (`toks[-1] not in EOS` misses EOS in the middle of a cycle's output), so its cycle counts / wall time are inflated for early-stopping tasks (a4, a6, b4, b5, c1, c4, c5; e.g. c5 'E 0.33'). `analyze.py` truncates the cycle list to the cycles that produced the kept tokens; measured ms/cycle is reported only for the 19 runs that hit the token cap.
- **Forced single-row cycles are not bit-identical to the natural stream:** 8 of 32 tasks diverge after 98-711 tokens (rounding near-ties); I use F's stream consistently for every policy, MTP-only included, so comparisons are paired.
- **Switch-style hybrids are a dead end in this engine**: no (n, m, L) cell passes the no-loss constraint in cross-validation (the CV falls back to MTP-only) because MTP's first-token accuracy (0.97-0.99) beats PLD's (0.6-0.9) even at l >= 3; L=3 / T=4 is a loss of 11-16% on a-c.
- **Not done:** no hybrid implemented or timed in the engine (V(T>4) is a model; the first task for an implementer); no tree / branch verification (DeltaNet's recurrent state cannot verify two branches in one step without per-branch state copies); no adaptive back-off simulated; sampling-mode acceptance of tail tokens not measured; no lm_head int8/int4+rescoring combination (E5: orthogonal, -6..-10% of V(T) would raise every ratio slightly).
